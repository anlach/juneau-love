# story

* [Delete photos](delete-photos.md) - A guest can delete the photos they uploaded, and an admin can delete any photo — batched over the same selection as download, confirmed once, with the backend enforcing the same rule as the UI gate.

# user-story

* [Access by approval status](access-by-approval-status.md) - A signed-in user's screen is determined by their approval state — pending sees an awaiting screen, rejected sees a rejection screen, approved sees guest content (admins additionally the registrations page).
* [Change display name](change-display-name.md) - A signed-in user changes the name the site shows for them from a menu-reached page that looks like the registration card; the save is a self-update of users.display_name (the only user-writable column), the header and the DB row follow, and an empty name is refused.
* [Download photos](download-photos.md) - Approved guests select gallery photos with checkboxes (hover-revealed per cell, all visible once a selection is active) and download them — one selection saves the original file directly, several save a single client-built zip.
* [Guest gallery](guest-gallery.md) - Approved guests share a gallery of images stored in a private S3 bucket — admin-seeded and guest-uploaded — with bytes reaching the browser only via short-lived presigned URLs. The grid loads client-generated WebP thumbnails; the full-size original loads on demand. Uploaders and admins can delete photos.
* [Register as a guest](register-as-guest.md) - A guest registers with email and display name (no password); the registration starts in pending state, the guest confirms their email, and then it waits for an admin decision. The admins are alerted about the new registration by email (with approve/reject links) as soon as it is made.
* [Review registrations (admin)](review-registrations.md) - The admin opens a registrations page listing every registration with its verification and approval state, and can approve (verified emails only) or reject each one; approving emails the guest their login link. The table also shows each guest's wedding and whale-watch RSVP counts (em dash while unset) and an expected-headcount total per event over approved rows, where an unset count counts for zero. Admins are alerted to each new registration by email with approve/reject deep links into this page.
* [RSVP for the wedding and the whale watch](rsvp-party-size.md) - An approved guest tells the hosts how many people in their party will attend the wedding AND the whale watch (the day before) via a two-field RSVP page — the landing card's primary action. Each count is null until first saved (0–8, where 0 means "not coming"); the guest may register a different number per event, and each count feeds its own admin headcount total, where an unset (null) count counts for zero.
* [Sign in with a login link](sign-in-with-login-link.md) - An approved guest gets a session by clicking a login link in an email — a native GoTrue magiclink, short-lived and single-use; a lost or expired session is recovered by entering the guest's email to get a fresh link.
* [Things to Do guide (guest content)](things-to-do.md) - Approved guests get a "Things to Do in Juneau (Like a Local on a Budget)" guide page — Morgan's email, formatted — with the 2019 travel map embedded as a static PDF and a download link; approval-gated like all guest content.
* [Whale watch page (guest content)](whale-watch.md) - Approved guests get a whale-watch info page for Friday, June 18, 2027 — the day before the wedding — meet at Statter Harbor by 2:45 PM, 3:00 PM departure, back at Statter Harbor by 6:00 PM, room for up to 120; with an RSVP button into the shared RSVP page; approval-gated like all guest content.
